A syntax highlighter can store its colors in a tiny image and leave the code as ordinary text. A static block needs only a `pre` and a `code`, regardless of how many tokens it contains. The same idea works on a native text field:

There is no colored text overlay here. The image supplies the colors; the textarea supplies the letters and editing behavior.

Separate the layers below. The lower plane holds a color for each character position. The upper plane supplies the shapes through which those colors are visible. Both follow the source and theme selected above.

<Layers />

Each image pixel expands to one monospace cell: `1ch` wide and one line-height tall. With `image-rendering: pixelated`, neighboring colors stay distinct. `background-clip: text` restricts them to the letters. The text remains selectable HTML, not pixels drawn into a canvas.

## From tokens to an image

Shiki supplies the tokens and their theme colors. Write those colors into an RGBA buffer, one row per source line, then encode it as a PNG. Inspect the actual intermediate data:

<Pipeline />

The tokenizer is unchanged in purpose. We replace the way its output reaches the screen. Canvas is just the browser's PNG encoder; it never draws the letters.

The static markup is simply:

```html
<pre><code>const answer = 42;</code></pre>
```

These are the essential alignment and clipping rules. The image dimensions supply `--columns` and `--lines`:

```css
code {
  display: block;
  font-family: monospace;
  line-height: 1.6;
  white-space: pre;
  font-variant-ligatures: none;
  background-image: url("colors.png");
  background-size: calc(var(--columns) * 1ch)
                   calc(var(--lines) * 1.6em);
  background-repeat: no-repeat;
  image-rendering: pixelated;
  background-clip: text;
  color: transparent;
}
```

This is the core mechanism. The working demos also handle selection, unsupported input, image readiness, printing and forced colors.

## What changes when there are no token elements?

A span renderer gives each token an element carrying its color. The image renderer keeps those colors outside the DOM. Increase the amount of code below; both sides use the same Shiki tokens and theme.

<Comparison />

The element count stays constant on the image side. The image dimensions and processing work still grow. Fewer elements alone do not establish that the full pipeline is faster.

The representation also changes integration: the image contains all token colors, so it needs no token classes or theme color stylesheet. Changing the theme replaces the image. Text metrics and clipping still require CSS.

## Editing adds a timing problem

A textarea already provides a caret, selection, copy and paste, and undo. Applying the color image directly avoids maintaining a second text layer. Each edit still requires a new image, and that image takes time to encode and decode.

Keeping the old image puts its colors under the wrong letters. This experiment adds a controllable delay to make the mismatch visible:

<Updates />

The editor at the top uses plain text while waiting, decodes the new image before applying it, and ignores results for older revisions. This prioritizes matching text and colors; it does not promise flicker-free editing across browsers. Composition input waits until composition ends before regenerating the image.

## Where the grid stops being enough

The simple mapping assumes one character per cell and one image row per visible line. Change those assumptions:

<Boundaries />

Wrapping requires a map of visual lines. Tabs need tab-stop expansion. Unicode needs a model of displayed columns, not `string.length`. Font metrics, spacing and ligatures must agree with the image. These demos highlight printable ASCII and newlines, up to 512 columns and 100 lines; other editor input falls back to readable plain text.

A color image also supplies no per-token bold or italic styles, links, or hover targets. Long lines widen the whole rectangular buffer, including the unused cells beside shorter lines.

## Scope and evidence

Static code display and small editable code fields are useful candidates: real text, no token elements, and a direct path from a tokenizer's colors to the browser. Rich editors would need additional solutions for layout, token interactions and large-document updates.
