Syntax highlighters often wrap tokens in separate elements. Large code blocks can produce thousands of nodes for the browser to parse, style, and keep in memory. Editing may also require updating that structure.

I want to show a way to render syntax colors with just **two elements**, regardless of the number of tokens.

## Put the colors behind the text

Use a tiny image: one pixel per character position, one pixel row per line. Scale it to match a monospace font, then use `background-clip: text` to show the image only inside the letters.

The image holds the colors. The letters are still real, selectable text.

The code block itself is just:

```html
<pre><code>const answer = 42;</code></pre>
```

These are the core styles. Set `--columns` and `--lines` from the image dimensions:

```css
code {
  display: block;
  font-family: monospace;
  line-height: 1.6;
  white-space: pre;
  font-variant-ligatures: none;
  background-image: url("colors.png");
  background-size: calc(var(--columns) * 1ch)
                   calc(var(--lines) * 1.6em);
  background-repeat: no-repeat;
  image-rendering: pixelated;
  background-clip: text;
  color: transparent;
}
```

Each image pixel covers one text cell. The demos also include readable fallbacks for missing images, printing, and forced colors.

## The theme travels with the image

No token classes or external theme stylesheet are needed. All syntax colors are in the image. Integration needs the original text, the image, and a few fixed CSS rules for alignment and clipping.

## Let the browser handle editing

The text field already handles the caret, selection, copy and paste, and undo. We update a background image instead of managing token elements or keeping a second text layer in sync.

That could make small code editors much simpler. It does not provide every feature of a full editor.

## Where it gets harder

- **Line wrapping:** Width changes can move text onto new visual lines. The image must be recalculated to match.
- **Tabs and Unicode:** Characters do not always occupy one cell. This demo supports printable ASCII and newlines; other input stays readable in plain text.
- **Font metrics:** Line height, spacing, and image position must agree. Ligatures and font changes need care.
- **Token features:** Colors alone cannot provide bold keywords, links, or hover targets. Theme changes need a new image.
- **Large inputs:** Tokenization, PNG encoding, and painting still cost time. A long line makes the whole image wider. This demo limits highlighting to 512 columns and 100 lines.
- **Browser behavior:** Scrolling, image failures, zoom, selection, and accessibility need testing on the target browsers.

> **Interactive placeholder — break the grid:** Resize a code block, enable wrapping, and insert a tab or emoji. Show where the simple mapping stops working.

The DOM stays small. Whether the whole pipeline is faster needs a fair benchmark with the same tokenizer and code. That is still an open question.
